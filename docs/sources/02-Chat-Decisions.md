# Решения из чата

> [!summary]
> Этот файл фиксирует не весь чат целиком, а устойчивые решения, которые уже были приняты в обсуждении и на которые можно опираться дальше.

## Продуктовая позиция

- Проект должен быть объяснимым R&D-ассистентом, а не генератором фантазий.
- Главная ценность: сокращать время старта НИОКР и делать выбор гипотез прозрачнее.
- Главная “фишка”: мультиагентный спор вокруг одной гипотезы.
- Не стоит делать knowledge graph главным лицом проекта, чтобы не смещать акцент с объяснимого hypothesis workflow.

## Канонический процесс

- На вход подаются KPI, ограничения и база знаний.
- Система ищет релевантные данные, удачные и неудачные подходы, а также противоречия.
- Система формирует первичную гипотезу.
- Гипотеза проходит debate loop.
- После этого подключаются evaluators.
- Затем Judge выдаёт финальную рекомендацию.

## Debate loop

- Внутри спора обсуждается одна и та же гипотеза.
- Обязательные роли: `Защищающий`, `Атакующий`, `Производственник`.
- Производственник находится внутри цикла, а не после него.
- Цикл можно повторять до трёх раз.
- Задача цикла: улучшить гипотезу, а не сделать декоративный диалог.

## Evaluation layer

- Базовые evaluators: `Finance` и `Risk`.
- Пользователь может добавлять дополнительные критерии.
- Пользовательские evaluators не спорят между собой.
- Дополнительные роли лучше добавлять в evaluation layer, а не в debate loop.

## Judge

- Судья собирает результаты debate и evaluation.
- Судья не должен придумывать полностью новую гипотезу “с потолка”.
- Судья должен дать приоритет, сильные и слабые стороны, риски, потенциальную ценность и следующий шаг проверки.

## Архитектурная линия

- Для быстрого рабочего контура достаточно простого RAG по чанкам и нескольких промптов.
- Для более сильной версии стоит идти в сторону PostgreSQL + pgvector.
- Оркестрацию лучше писать явно в Python-коде.
- Каждый агент по сути должен быть управляемой ролью с prompt + schema, а не неуправляемым автономным существом.

## UX-линия

- Не делать обычный чат.
- Показывать спор как сцену.
- Хранить историю версий гипотезы.
- Отдельно показывать evidence, debate, evaluation и final recommendation.
- Визуально продукт должен быть ближе к интерактивной сцене или ретро-визуальной новелле, чем к стандартному корпоративному дашборду.

## Что уже отражено в репозитории

- В текущем frontend-прототипе уже есть визуальная композиция с debate stage, evaluators, judge, сессиями и вложениями.
- В backend пока есть только минимальный сервисный каркас.
- В infra уже собран рабочий локальный docker-контур с nginx proxy для `/api`.

## Открытые вопросы

> [!question]
> Эти темы ещё стоит дожать в следующих итерациях документации или проектирования:

- точный формат сущности `evidence_item`;
- где именно хранить версии гипотезы и transcript debate;
- нужен ли фоновый execution model для долгих запусков;
- насколько глубоко идти в extraction `claims / facts` уже в MVP.
